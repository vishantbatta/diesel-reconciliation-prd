Diesel Reconciliation Dashboard

A daily dashboard that turns site-level diesel records into a red flag within two or three days, and then narrows the blame to the machine most likely causing it. Scope for V1 is diesel only.

01

Background

Diesel leaks quietly on construction sites, and by the time anyone notices, the money is gone. The case that triggered this project: an earthworks job worth roughly one crore, where diesel spend landed at ₹50–60 lakh against an expectation of about ₹35 lakh. The overrun ran for two to three months before a director pulled the records himself and found it. The data was there the whole time — site diesel was being captured every day. What was missing was any comparison against what the machines should have burned.

That detail shaped the whole product. The loss surfaced as a site-level number first, and only later got narrowed to specific machines. We are building exactly that workflow, because machine-level fuel metering does not exist on these sites and nobody is going to install it for V1.

₹50–60L

5–6%

Real construction margins, against the 10% everyone plans for. One caught leak pays for the tool.

02

Product approach: two layers, never mixed

The dashboard answers two questions, and they are not the same kind of question. The first — is this site burning too much diesel? — is arithmetic, and it is the only number we defend without caveats. The second — which machine is causing it? — is a statistical claim, and the interface has to declare that every single time it shows one. The first wrong accusation would cost more trust than ten missed leaks are worth.

Layer 1

Site reconciliation — is this site over?

Actual site diesel issued, compared against what the machines should have burned at their norms. Displayed daily, judged on a seven-day rolling window.

Certain
Runs only when the site is amber or red
Layer 2

Machine attribution — who is likely responsible?

Diesel is recorded per site, so no machine has a measured fuel number. We infer one from how site diesel moves with each machine's hours, and return a ranked list with confidence — never a verdict.

Probable

The mental model

A site's diesel bill behaves like a household electricity bill. You find the guilty appliance by watching which one's usage moves in step with the bill across weeks. Same idea here, with machines and tanker fills.

Attribution is not the only signal

Usage data alone can flag trouble even when fuel cannot be split: abnormal idle ratios, run hours beyond physical capacity, night running, hours spiking without output. These run independently of Layer 2.

Honesty constraints

An inferred machine number is never displayed as a measured one. If the data cannot separate the machines, the tool says so and shows site level only. Below 50% confidence it names nobody — the gap is reported as unattributed.

Unattributed is a finding, not a failure

Whatever the machines cannot account for is reported as unattributed variance. It has real causes: tank-level loss, DG sets and small tools that carry no telemetry, or pilferage. A large unattributed share points the investigation somewhere useful.

V1 delivery note — alerts by email

V1 has no mobile app and no notification centre. Alerts reach users by email: a daily digest in the morning (site statuses, new suspects, sync issues) plus an immediate email when a site goes red or a streak escalates. Recipients are configured per project — typically the project manager, stores, and the director. In-app notifications and WhatsApp are V2 candidates; see Future scope.

06

Technical design

Data flow

Capture

  • ConnectorsSite diesel from SAP or stores. Machine hours and kilometres from OEM telematics.
  • Raw ingest logEvery payload stored with its source reference. Nothing overwritten, ever.
→

Compute

  • Identity mapping and validationOEM serial → machine → site, resolved per day. Bad records quarantined, not dropped.
  • Site daily diesel and machine usageThe two clean inputs everything else reads.
  • Layer 1Site reconciliation, exact arithmetic.
  • Layer 2 + anomaly scanAttribution, confidence, usage flags. Only for sites that are amber or red.
→

Surface

  • DashboardSite cards, drill-down, suspect list, trend.
  • Email (V1)Morning digest plus immediate mail on new red sites and streak escalations.
  • AlertsAlso visible in the console's Alerts page with delivery status.

Layer 1 math — exact

ideal_site_day = Σ ( machine_hours × norm ) + other_use_allowance variance = actual_site_diesel − ideal_site_day

Displayed daily for freshness, but judged on a seven-day rolling window, because fills are irregular and single days are noisy. The other-use allowance per site covers DG sets, small tools and site vehicles that burn diesel but carry no telemetry. Without it, every machine on the site looks guilty.

Layer 2 math — inference

issued[t] ≈ Σ β[machine] × hours[t]

Fit daily site diesel against each machine's hours across a window, using least squares with ridge regularisation — machines that move together would otherwise produce fake certainty. Output per machine: implied litres per hour, deviation from norm, confidence, rank. Attribution needs at least fourteen days of history and some variation in schedules; below that it is suppressed and the tool shows site level only.

Triggers

On every successful sync

Rebuild the affected site days, recompute Layer 1, and if the site is amber or red run Layer 2 plus the anomaly scan, then update the dashboard and queue email changes for the digest.

Scheduled syncs

Every one to four hours per source, with a full daily close at 23:00.

Retro source edit

A corrected record recomputes the affected day and keeps the audit entry.

New machine mapped

Its history is backfilled automatically.

Sync failure or no data by cutoff

A sync-health alert emails IT or stores immediately. Never a calm-looking blank dashboard.

Weekly

Norms recalibrated from history and emailed for approval before they take effect.

Status conditions

Green

Within 10% over, on the seven-day rolling window.

Amber

Between 10% and 25% over.

Red

More than 25% over. Attribution starts here.

Grey

No diesel or no usage data. Never rendered as green.

Machine red

Implied litres per hour above norm by more than 25%, and confidence at 80% or higher.

Machine amber

A deviation is present, but confidence sits between 50% and 80%.

Not listed

Below 50% confidence the machine is not named at all. The gap is reported as unattributed.

Fuel without work

Site diesel above zero while total hours are close to zero.

Streak escalation

Three or more consecutive red days raises an escalated email to the director, not just the PM.

Unattributed 30%+

More than 30% of the excess unaccounted for is flagged as likely non-machine loss: tank, pilferage or other.

Email alerts (V1)

Email is the only alerting channel in V1. Three mail types:

Daily digest (07:30). One email per project: every site with its status and seven-day variance, machines newly listed as suspects, any alerts opened or closed yesterday, and sync problems. Plain text plus a link into the console.

Immediate red alert. Sent as soon as a site crosses into red or a three-day streak escalates. Goes to the PM; streak escalations add the director.

Weekly ranking (Monday). All sites ranked by variance, same content the director sees on the dashboard.

Every alert shown in the console records which mail went out, to whom, and when — so the dashboard and the inbox never disagree. Recipients are configured per project at setup; no self-serve subscription management in V1.

Validation rules

Litres at or above zero. Hours at or below twenty-four. Duplicates deduped on source reference. Unmapped or invalid records quarantined, never silently dropped. Every displayed number traceable to its source record. Attribution never computed from fewer than fourteen days of history.

07

Assumptions and open questions

  • Field meanings. Diesel is litres and value is rupees. If value turns out to be a meter reading, it is treated as cumulative and the same pipeline uses deltas.
  • Site-level diesel is permanent. Records are per site per fill, not per machine. Accepted by design, not a temporary gap.
  • Usage is near-daily and per machine. Arrives with the OEM serial or asset code, not in monthly lumps.
  • One site per machine per day. Machines that move between sites are attributed day by day to where they worked.
  • Norms are directionally right. History refines them weekly, with approval.
  • Attribution is probabilistic by nature. A known, accepted limit — not a bug awaiting a later fix.
  • Email reaches people. V1 assumes project email distribution lists exist and are read. If a site's PM does not read email, the alert effectively does not exist — to verify during pilot.

Confirm early — biggest unknown

Does each site have one tank with a dispenser meter, or multiple separate fills? Meter readings give far better timing, and the answer decides how much daily resolution this dashboard can ever have.

Confirm early — email recipients

Who exactly should receive the digest versus immediate red alerts, per project? We should collect named recipient lists during the pilot rather than invent a default.

08

Edge cases

DG sets, small tools, canteen, site vehicles

They burn diesel and appear in no telemetry. The configurable other-use allowance per site absorbs them; without it, every machine looks guilty.

Contractor-supplied diesel

Those machines are excluded from ideal, otherwise the site looks over budget by design.

All machines on identical schedules

Mathematically inseparable. Report site level only, and say why in the UI.

Single-machine site

Site variance is machine variance. Attribution becomes exact.

Irregular tanker fills

Judge on rolling windows and mark estimated days as estimated.

Meter reset or tank replacement

Detect the step and do not book it as consumption.

Machine moved between sites

Attribute per day to the site where it worked.

OEM data lag

Mark the day as awaiting source, never green. The sync-health page shows the lag.

New or unmapped machine

Exception queue; backfilled automatically once mapped.

Duplicate sync or retro SAP edits

Dedupe, recompute, keep the audit trail.

Legitimately heavy usage

Hard terrain, deeper excavation, long leads. Acknowledged with a cause, kept in history — the site is not "wrong", the norm was.

Idle machine fueled

Site flag for fuel without work, not an infinite variance.

Email undeliverable

Bounce on an alert address raises a sync-health issue, same as a failed feed.

09

Future scope

Flow meters or fuel sensors on large machines — attribution moves from inference to measurement.

Per-machine dispenser logs, manual or IoT, as an optional accuracy upgrade.

WhatsApp morning digest alongside, or instead of, email.

In-app notification centre with subscription management.

The same two-layer pattern applied to manpower, materials and overheads.

Cross-project benchmarking, so machinery capex is decided on data rather than trust.

Predictive maintenance from fuel and idle anomalies.

Pilferage pattern detection across sites, shifts and operators.

Success test: the site is red by day two or three.

EX-14 surfaces as the top suspect with a confidence figure attached, instead of the director finding it in month three. The certain-versus-probable distinction stays visible at all times, because the first wrong accusation costs more trust than the tool can buy back.
